* Why compare tools
:PROPERTIES:
:BEAMER_opt: pg=2
:END:
#+beamer: \slidegraphics{figures/workflow-alternatives/gtext}
#+attr_latex: :options [x=69,y=150,s=15.9,l=26,ind=16.06,bf=arial]
#+begin_tb
- Many small tasks inside one Slurm allocation need a tool that starts a task as soon as a core is free.
- QCG-PilotJob is one such tool. HyperQueue, Snakemake and FireWorks are three others.
- Each one expresses "this task waits for those tasks" differently.
- The comparison: how the dependency is written, and how much of the allocation sits idle.
#+end_tb

* What the idle time comes from
:PROPERTIES:
:BEAMER_opt: pg=9
:END:
#+beamer: \slidegraphics{figures/workflow-alternatives/gtext}
#+attr_latex: :options [x=69,y=150,s=15.9,l=22,ind=16.06,bf=arial,p=8]
#+begin_tb
- The bash pipeline runs tasks in blocks of the slot count, so a block waits for its longest task.
- QCG-PilotJob: most of the 23% came from the module load each task did in that run. The examples \\
  leave *modules* out, so the tasks inherit the job's environment.
- HyperQueue and Snakemake start the next task when a slot frees up: 2% idle.
- Plot lanes show the CPU number a task reported at start. Tasks are not pinned, so overlapping \\
  bars can leave white space that is not idle time.
- The idle figure comes from the task start and end times.
#+end_tb

* How to choose
:PROPERTIES:
:BEAMER_opt: pg=10
:END:
#+beamer: \slidegraphics{figures/workflow-alternatives/gtext}
#+attr_latex: :options [x=69,y=150,s=15.9,l=22,ind=16.06,bf=arial,p=8]
#+begin_tb
- *QCG-PilotJob* and *HyperQueue*: many tasks inside one allocation. QCG-PilotJob is driven \\
  from Python; HyperQueue from the command line, with a Python API as well.
- *Snakemake*: rules on files; a rerun builds only what changed.
- *FireWorks*: a database of workflows with states and reruns. Not for many small tasks: \\
  without a MongoDB server one worker runs them in turn, 212 s for 1000 averages (Snakemake 15 s).
#+end_tb
